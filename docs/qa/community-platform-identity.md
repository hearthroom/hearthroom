# 社群身分與遊玩平台分離

需求：Hearthroom 成員只有一份社群 NSFW 設定；綁定的遊玩帳號提供登入、模型服務及點數，不提供第二份成人內容偏好。

驗收：跨平台查看成人卡片時，以目前社群登入身分讀取成員設定；選擇遊玩服務後才使用該服務的綁定憑證。社群設定關閉或未驗證時仍拒絕成人公開讀取。

本次範圍：修正平台查詢的身分及卡片識別。不修改上游、帳號資料、點數或內容審核規則。

## 修正

- `fetchCardPlatforms` 不再接受卡片供應商作為驗證身分；沿用其他社群公開 API 的訪客標頭。
- `CardPlatforms` 使用 Hearthroom `card.id` 查詢，避免將供應商的 role ID／託管副本 ID 當成社群卡片 ID。
- 卡片的 provider 只作為遊玩選項的初始選擇；實際遊玩保留綁定帳號、憑證及 chat scope 檢查。
- 後端每次平台請求仍驗證同一份 Hearthroom 成員 NSFW 設定，沒有增加供應商成人偏好檢查。

## 驗證

- Red：兩種登入平台的跨平台查詢都得到 `nsfw_gated`；卡片頁錯用 `role-abc` 查詢，而非社群 ID `abc`。
- Green：新增 API／頁面回歸及真實 Worker/D1 測試。兩種綁定身分都讀到同一個成員的設定；關閉及未驗證仍 403。
- 完整可信集：Worker 500、web 451 通過；真實卡片探測因缺少 `REAL_CARDS_DIR` 跳過。型別檢查、固定版本 Stage 建置、web 正式建置通過。
- 初次全量測試失敗歸因：HTML 資源尚未完成建置；待建置完成後重跑解除。第二次發現成人流程測試的 URL 前綴替身誤把平台回應當卡片物件；補上正確平台回應後，最終全量通過。
- Chrome 自然路徑（本機合成資料、實際 Worker）：匿名開成人卡片顯示社群門；透過 HarperHarbor OAuth 登入後，LunaTalk 卡片平台 API 回 200，顯示 LunaTalk 選項與開始對話。連接合成遊玩憑證後進入 `/play/...?...provider=lunatalk`，播放器控制列出現，未出現第二份 NSFW 設定；回卡片仍可查看，顯示合成帳號的點數。
- 合成上游只實作本次登入／公開卡片路徑，播放器其他 API 不完整；不宣稱完整對話、串流或計費驗收。未發送模型請求，未修改正式帳號或卡片。桌面畫面檢查完成；無版面或文案變更，未追加手機視覺驗收。
