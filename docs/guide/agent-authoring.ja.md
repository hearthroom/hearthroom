## エージェントに任せられること

エージェントは公式のカード作成スキルに沿って動きます。何を作りたいかを把握し（解釈が分かれて別のカードになる場合のみ確認し、それ以外は自分で判断して）、カードをフォルダとして書き、試用カードとしてアップロードし、自分でチェックと試しプレイをして、改善点を伝えてくれます。各項目に、そのまま入力できるプロンプトを添えています。

### アイデアからカードを一枚作る

> 「修仙カードを書いて。俺は宗門を追い出された落ちこぼれで、姉弟子がこっそり助けてくれる。緊張は、彼女が動いた瞬間に発覚すること。表示する状態は修為だけ。まず試用カードにして、一番弱い層を教えて」

ぼんやりしたアイデアでも大丈夫です。設定、人物、関係、最初のメッセージを一緒に固めてから書き始めます。

### 手元のカードを直す

> 「この SillyTavern のカードを読み込んで、三往復で話が続かなくなる理由を教えて。それから直して」

SillyTavern の PNG・JSON・CHARX と、魅魔島（MMD）の 3 点セットをそのまま読み込めます。

### ステータスバー、テーマ、全画面のレイアウトを作る

> 「好感度と現在地を表示するステータスバーを足して、最初のメッセージをレンダリングして見せて」

画面が必要なときは、ツールキット付属のサンドボックスキット（モデルが書くステータスブロックをパネルに、選択肢ボタン、テーマ）を使い、`hearthroom card check` でフォルダを検査し、`hearthroom card preview` と `card render` で結果を確認します。ルールを何も書かなくても、返信末尾の [status]／[choices] ブロックはページ自身がパネルとボタンに描きます。独自の見た目、テーマ、ピン留めバーが欲しいときにキットを使います。

チャットページ自体はオープンソースです（`hearthroom/moonstage`、このサイトの `stage` サブモジュール）。skills のサンドボックス契約はその `src/sandbox/` から生成され、未記載の事柄についてはプラットフォーム事実ページが読むべきファイルを示します。

### 試しプレイで問題を見つける

> 「2 つ目の最初のメッセージで 10 往復プレイして、プレイヤーが何往復目で飽きるか、その理由を教えて」

### 公開前のチェック

> 「このカードを審査に出せるかチェックして、直すべきところを挙げて」

## エージェントがカードを作る流れ

1. **フォルダとして書く**：長文は Markdown ファイル、世界設定・ルール・画像はそれぞれ別ファイル。自分で開いて読んだり直したりもできます。
2. **試用カードにする**：自分だけが見られ、最後の更新から 3 日で期限切れ。同時に 5 枚まで持てます。
3. **チェックとレンダリング**：プラットフォームのルールで文字数と内容を確かめ、最初のメッセージにルールを当ててレンダリングし、ステータスバーやレイアウトを確認します。
4. **試しプレイ**：実際にキャラクターと 1 往復して、返答が保つか、プレイヤーが続けられるかを見ます。
5. **修正**：結果をもとに直し、またアップロードして試す、を納得いくまで繰り返します。
6. **残す**：満足したら非公開の正式なカードとして保存し、マイカードに表示されます。審査への提出と公開はサイトであなたが決めます。

## プロンプトガイド

エージェントは公式スキルに沿って動作するため、カードの書き方を説明する必要はありません。必要なのは、スキルに含まれない情報です。プレイヤーの状況、キャラクターの声、求める画面、完了の基準、そしてエージェントが自分で判断してよい範囲。このセクションは「よくある状況」ごとに整理し、各項目でエージェントがなぜそう動くのか、何を書けばよいかを説明し、そのままコピーして使えるプロンプトを添えています。まず、あてはまる項目を探してください。

- 出来上がったカードがほかと変わらない：[ジャンルだけでなく状況と緊張を伝える](#ジャンルだけでなく状況と緊張を伝える)、[形容詞の代わりに台詞を一行](#形容詞の代わりに台詞を一行)
- ステータスバーやボタンが物語より目立つ：[画面の種類と、不要な既定パターンを伝える](#画面の種類と不要な既定パターンを伝える)
- 質問が多く、各段階で確認を待つ：[完了の基準と、任せる範囲を書く](#完了の基準と任せる範囲を書く)
- まだ考えがまとまらない：[カードの前に方向を出してもらう](#カードの前に方向を出してもらう)
- 原作・設定・好きなカードがある：[素材をそのまま渡す](#素材をそのまま渡す)
- 言語・言葉づかい・呼び方が合わない：[言語と呼び方を伝える](#言語と呼び方を伝える)
- 内容の範囲が想定と違う：[内容の範囲を伝える](#内容の範囲を伝える)
- 依頼していない内容が変更された：[1 つの版で直すのは 1 つ](#1-つの版で直すのは-1-つ)
- テスト済みと言うのに 3 往復で尽きる：[本格的なプレイテストを求め、作業記録を読む](#本格的なプレイテストを求め作業記録を読む)
- 直したらかえって悪化した：[現象を伝え、直し方は指定しない](#現象を伝え直し方は指定しない)
- 質問しただけなのに変更された：[意見だけが欲しいときは先に言う](#意見だけが欲しいときは先に言う)
- 新しい会話で続きを頼む：[前回の続きから](#前回の続きから)

### ジャンルだけでなく状況と緊張を伝える

「面白いメイドのカードを書いて」のような依頼はジャンルしか渡していないので、エージェントはそのジャンルで最も一般的なカードを書きます。よくある設定、よくある関係、よくある導入。スキルが保証するのはカードの構造であって、このカードの見どころは決められません。見どころは 2 つから生まれます。プレイヤーが誰で何に直面するか（状況）と、何が未解決のままか（緊張）です。書き始める前に、エージェントはそのジャンルの一般的な書き方と、このカードがどう違うかを説明します。異論はその段階で伝えてください。

こう書きます：

```text
メイドのカード。プレイヤーは古い屋敷を相続したばかりの若い当主。彼女は前の当主が残した家政婦で、この屋敷の口にできない事情をすべて知っている。緊張：プレイヤーが信頼を得るたびに秘密を一つずつ渡すが、渡すごとに彼女が屋敷に残る理由が一つ減る。まず、一般的なメイドのカードとどう変えるつもりかを説明してから始めて。
```

最後の一文が要です。エージェントに「一般的な版」を先に言わせることで、書き始める前に方向を変えられます。

### 形容詞の代わりに台詞を一行

「自然な台詞」「個性的に」「ツンデレ」のような形容は人によって解釈が違い、エージェントは最も一般的な解釈を当てるしかありません。求める声の台詞を一行示せば、口調、文の長さ、呼び方、どこまで言わないかが決まり、どんな形容詞より正確です。

こう書きます：

```text
彼女の声はこの一行に倣う：「旦那様、あの扉の鍵は、まだご入用ではないかと。」短い文、敬語、理由は説明せず、言い終えたら止まる。この声で場面の違う台詞を 3 つ書いて見せてから、カード全体に進んで。
```

台詞の見本は一行で足ります。3 つ以上渡すと、エージェントは声ではなく文型を真似し始めます。

### 画面の種類と、不要な既定パターンを伝える

カードの画面は 2 種類です。物語が主で画面は補助か、遊びが数値と結びつき画面が中心か。伝えなければ、エージェントはジャンルの定番を当てはめます。好感度メーター、毎回の返信に 2〜4 個のボタン、感情の数値化。「AI っぽくしないで」はどのパターンにも対応しないため、エージェントには判別できません。不要な既定パターンを名指しすることが効きます。なお、表示ルールがなくても、プラットフォームは返信末尾の [status]／[choices] ブロックをパネルとボタンとして描画します。画面が必要かどうかと、ルールが必要かどうかは別の問題です。

こう書きます：

```text
これはコンパニオンカード。物語が主で、画面を切っても読めること。好感度メーター、毎回の返信に付く選択肢ボタン、感情の数値化は不要。返信の末尾に一行だけ残す：彼女が今どこにいて、何時か。
```

遊びが数値と結びつくカードでは逆に伝えます：

```text
これはサバイバルカードで、画面が中心。表示する状態は水位・食料・燃料の 3 つだけで、どれもプレイヤーの行動で変わること。毎ターンの末尾に 2〜4 個の選択肢。プレイヤーが変えられない数値は表示しない。
```

### 完了の基準と、任せる範囲を書く

エージェントが止まって質問するのは、課題が難しいからではなく、どこまでで完了か、何を確認なしに進めてよいかが分からないからです。「まず設定を見せて、次に人物、それから最初のメッセージ」と頼むと、各段階で止まって待ちます。完了の基準と、自分で判断してよい範囲（クレジットの上限を含む）を書き、残りは任せてください。

こう書きます：

```text
完了の基準：試用カードとしてアップロードし、自分で 10 往復プレイし、最も弱い層を報告すること。試用カードのアップロードと修正に確認は不要。クレジットは 50 までは自分の判断で、超えるなら確認して。確認が要るのは、審査提出、公開、まったく別のカードになる選択だけ。
```

この指示は、曖昧な依頼について質問する頻度も下げます。もっと確認してほしい場合は、最後の一文を外してください。

### カードの前に方向を出してもらう

考えがまとまっていないとき、「任せる」はすべての判断を渡すことになり、返ってくるのはたいていそのジャンルの最も一般的な版です。方向を見ないうちに完成品を求めると、一枚分の作業が無駄になります。まず方向をいくつか出してもらい、それぞれプレイヤーが何をし、緊張がどこにあるかを一文で示させ、一つを選んでから進めます。

こう書きます：

```text
終末もの。まず方向を 3 つ、それぞれプレイヤーが何をし、緊張がどこにあるかを一文で。カードはまだ書かない。私が選んでから始めて。
```

### 素材をそのまま渡す

二次創作の原作、自分でまとめた設定、好きなカードは、エージェントが自分では作れない情報です。「あのアニメの冷たい先輩みたいに」は記憶からの再構成を求めることになり、結果はずれます。素材を渡し、何を残し何を変えてよいかを伝えてください。好きなカードを添えるときは、どの部分が欲しいか（テンポ、導入、台詞の密度）を言わないと、題材まで真似されます。

こう書きます：

```text
原作は『〔作品名〕』の〔キャラクター名〕。設定は以下に添付。必ず残す：後輩への呼び方、「まず動く」癖。変えてよい：時系列を卒業後 1 年目に。好きなカードも添付するが、欲しいのは最初のメッセージのテンポで、題材ではない。
```

### 言語と呼び方を伝える

カードの言語、言葉づかい、キャラクターからプレイヤーへの呼び方は、エージェントが自動では分かりません。「日本語で書いて」では、敬体か常体か、名前で呼ぶかどうかが決まりません。最初に伝えておくと、あとで欄ごとに直す手間が省けます。

こう書きます：

```text
全体を日本語で。キャラクターはプレイヤーに敬語を使い、「あなた」ではなく名前で呼ぶ。プレイヤーの名前はプレイヤーが入力するので、カード側で決めない。
```

### 内容の範囲を伝える

「あまり際どくしないで」「やりすぎないで」には範囲がなく、エージェントには線が分かりません。既定の対象年齢、プレイヤーから求めた場合にどこまで応じるか、越えない線を伝えることで、エージェントはプラットフォームの規約とあなたの意図の両方を守れます。

こう書きます：

```text
既定は全年齢で、キャラクターから親密な関係に進めない。プレイヤーから求めた場合は手をつなぐ、抱きしめるまでで応じ、それ以上は物語で場面を変える。プラットフォームの規約はそちらで守り、この指示と衝突するときは規約を優先して知らせて。
```

### 1 つの版で直すのは 1 つ

「最初のメッセージが長い、好意を示すのが早い、世界観が薄い、名前も変えて」と頼むと複数箇所が同時に変わり、どの変更が効いたか分からなくなるうえ、頼んでいない箇所まで動きがちです。1 つの版につき 1 項目だけを指定し、残りは一覧にして触らないよう頼みます。

こう書きます：

```text
この版は「好意を示すのが早い」だけを対応して。ほかに気づいた問題は一覧にして、変更しない。完了したら、変更したファイルと各ファイルの変更内容を教えて。
```

### 本格的なプレイテストを求め、作業記録を読む

「テストした？」への答えはたいてい「した」で、エージェント自身の 2 往復では最初のメッセージが機能することしか確認できません。カードが持続するかは 10 往復以降で分かり、弱いモデルから先に問題が出ます。本格的なプレイテストはクレジットを消費するため、エージェントは事前に費用を伝えます。終了後は要約だけでなく、カードフォルダの `README.md` も確認してください。各版の決定、見送った方向、根拠を記録した作業記録です。

こう書きます：

```text
弱いモデルと強いモデルで各 10〜20 往復、毎回新しい会話でプレイして。何往復目から持たなくなるか、その原因を報告し、結果を README.md に記録して。開始前にクレジットを提示して。
```

### 現象を伝え、直し方は指定しない

「定義の第 2 段落を短くして」は処方の指定です。あなたが見ているのはプレイしたときの効果で、エージェントが見ているのはカード全体の構造です。原因は思っている段落にないことがよくあります。観察した現象を伝え、原因を探してもらい、「修正済み」の報告ではなく、同じ会話で前の版と比較するよう求めてください。

こう書きます：

```text
3 往復目で彼女から好意を示している。もっと遅くしたい。原因を特定してから修正し、修正後に同じ会話で前の版と比較して見せて。
```

### 意見だけが欲しいときは先に言う

「このカードはストーリー路線にすべき？」は質問に見えますが、エージェントには、尋ねているのか変更を求めているのか判別できません。両方が混在すると実行を選びます。意見だけが欲しいときは、その旨を明示してください。

こう書きます：

```text
まだどのファイルも変更しないで。このカードでストーリー路線とコンパニオン路線のそれぞれの代償は？説明したら私の判断を待って。
```

### 前回の続きから

新しい会話では、エージェントは前回の内容を覚えていません。「あのカードの続きをやって」では、最初から推測することになります。カードフォルダの `README.md` が作業記録なので、変更の前にまず読んでもらいます。

こう書きます：

```text
cards/maid のカードを続けて。まずフォルダの README.md を読み、前の版がどこまで進んだか、何が未対応かを報告してから始めて。
```

### 送信前の確認

- プレイヤーが誰で何に直面するかを伝えたか、ジャンル名だけで済ませていないか。
- キャラクターの声を台詞の一行で示したか、形容詞だけになっていないか。
- 画面はどちらの種類か、不要な既定パターンは何かを伝えたか。
- 完了の基準と、エージェントが判断してよい範囲（クレジット上限を含む）を書いたか。
- このプロンプトは 1 つのことだけを求めているか。

## クレジットと範囲

- 下書き、アップロード、チェック、レンダリングにクレジットはかかりません。
- 試しプレイは 1 往復ごとにクレジットを使うので、エージェントが始める前に確認します。
- 触るのは試用カードとあなた自身の非公開カードだけで、審査への提出や公開を勝手にすることはありません。
