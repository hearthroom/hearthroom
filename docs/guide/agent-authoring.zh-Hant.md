## 能交給 Agent 的事

Agent 依官方寫卡技能工作：釐清你的需求（只在不同理解會產生不同卡片時才向你確認），把卡寫成資料夾、推成試玩卡，自行檢查與試玩，再回報還能改進的地方。每一項都附一句可以直接輸入的提示詞。

### 從一個點子寫出整張卡

> 「寫一張修仙文的卡：我是被逐出宗門的廢柴，師姐偷偷幫我，要有修為和好感度兩個狀態，先做成試玩卡。」

只有模糊的想法也可以。Agent 會先與你釐清設定、人物、關係與開場白，再開始撰寫。

### 修復現有的卡

> 「匯入這張 SillyTavern 卡，告訴我為什麼聊三輪就沒話說，然後修掉。」

SillyTavern 的 PNG、JSON、CHARX 和魅魔島三件套都能直接匯入。

### 製作狀態欄、主題或整頁介面

> 「加一個顯示好感度和所在地點的狀態欄，渲染開場白給我看。」

需要畫面時，Agent 使用工具包內建的沙盒套件（把模型寫的狀態區塊畫成面板、選項鈕與主題），以 `hearthroom card check` 檢查資料夾，再以 `hearthroom card preview` 與 `card render` 檢視結果。即使沒有任何顯示規則，平台也會把回覆結尾的 [status]／[choices] 區塊畫成面板與按鈕；需要自訂樣式、主題或釘選列時才使用套件。

聊天頁本身是開源的（`hearthroom/moonstage`，本站的 `stage` 子模組）：skills 的沙盒契約由它的 `src/sandbox/` 生成，文件未涵蓋的部分，平台事實頁列出應讀取的檔案。

### 試玩並找出問題

> 「用第二個開場白玩兩輪，告訴我玩家會在哪裡失去興趣。」

### 上架前的檢查

> 「檢查這張卡能不能送審，列出還要修的地方。」

## Agent 怎麼寫卡

1. **寫成資料夾**：長文是 Markdown 檔，世界書、規則和圖片各有自己的檔案，你可以直接開啟檢視或修改。
2. **推成試玩卡**：只有你看得到，最後一次更新後 3 天過期，同時最多 5 張。
3. **檢查與渲染**：依平台規則檢查字數與內容，把開場白套上規則渲染出來，確認狀態欄和版面正確。
4. **試玩**：實際與角色對話一輪，確認回覆能否延續、玩家是否接得下去。
5. **修改**：依結果修改，再推送、再試玩，直到你滿意。
6. **保存**：滿意之後存成正式的私人卡，出現在「我的卡片」。送審和公開由你在網站上決定。

## 提示詞指南

Agent 依官方技能工作，不需要你說明寫卡的方法。需要你提供的是技能裡沒有的資訊：你要的玩法、目的、參考樣本，以及 Agent 可以自行決定的範圍。以下依常見狀況分節，每節附一組效果較差與效果較好的提示詞。

### 產出的卡太普通

只提供題材時，Agent 會寫出該題材最常見的版本。提供玩家的幻想與核心張力、一張你喜歡的卡，或一句你想要的對白，比「自然一點」「有個性」這類形容更有效。開始撰寫前，Agent 會先說明這個題材一般會怎麼寫、這張卡打算有什麼不同；不同意時在這一步提出。

> 效果較差：「寫一張修仙卡，對白自然一點、有個性一點。」

> 效果較好：「修仙卡。玩家是被逐出宗門的廢柴，師姐暗中相助，張力在於她一旦出手就會被發現。她的語氣參考這句：『這題我不接。進歌。』短、乾、不解釋。先說明你打算如何與一般的修仙卡不同。」

### Agent 頻繁提問，每一步都等待確認

Agent 停下來提問，通常是因為不清楚完成的標準，或不確定哪些事可以不經確認。先說明完成的標準與可自行決定的範圍，其餘由 Agent 處理。

> 效果較差：「先寫設定給我看，再寫人物，再寫開場白。」

> 效果較好：「完成的標準：推成試玩卡、你自己試玩過、告訴我最弱的一層。推送不需要確認；點數 50 以內自行安排，超過再問我。」

### Agent 修改了未要求修改的內容

「整體再好一點」會讓 Agent 同時修改多處，事後無法判斷哪項修改有效。每個版本只指定一件事，其餘請 Agent 記錄下來。

> 效果較差：「開場白太長、她太快示好、世界觀太薄、名字也換一下。」

> 效果較好：「這個版本只處理『她太快示好』，其餘列出來先不動。改完告訴我修改了哪些檔案。」

### Agent 表示已測試，實際對話三輪就無法延續

Agent 自行試玩兩輪，只能確認開場白可以運作；卡片能否延續要看十輪之後，較弱的模型最先出現問題。完整的試玩會消耗點數，Agent 會先告知費用。試玩結束後，除了總結，也請查看卡片資料夾中的 `README.md`：這是 Agent 的工作紀錄，包含每個版本的決定、否決的方向與證據。

> 效果較差：「你測過了嗎？」

> 效果較好：「用一個較弱的模型和一個較強的模型各試玩 10–20 輪，每次新開對話，告訴我從第幾輪開始無法延續、原因是什麼。開始前先告知點數。」

### 狀態欄與按鈕蓋過故事

卡片的畫面分兩種：故事為主、畫面輔助；或玩法與數值綁定、畫面為核心。先說明你要哪一種，再指出不要的預設做法。「不要太像 AI」無法對應到具體的模式。另外，即使沒有任何顯示規則，平台也會把回覆結尾的 [status]／[choices] 區塊畫成面板與按鈕；是否需要畫面，與是否需要撰寫規則是兩個問題。

> 效果較差：「加個狀態欄，好看一點，不要太像 AI。」

> 效果較好：「這是陪伴卡，故事為主，關閉畫面後也要能閱讀。不要好感度條、不要每則回覆附三個按鈕；只保留一行她目前的位置與時間。」

### 修改後反而更差

描述你觀察到的現象，不要直接指定修改方式。Agent 能看到整張卡的結構，你能判斷實際遊玩的效果；兩者結合才能找到原因。請 Agent 與上一版比較，而不是只回報「已修正」。

> 效果較差：「把定義第二段改短。」

> 效果較好：「第三輪她就主動示好了，我希望慢很多。請找出原因，修改後用同一組對話與上一版比較給我看。」

### 只是提問，Agent 卻直接修改

只想聽取意見時，明確說明只需要意見。Agent 能區分提問與要求，但兩者混在一起時，會選擇執行修改。

> 效果較差：「這張卡是不是該走劇情路線？」

> 效果較好：「先不要修改。這張卡走劇情或陪伴各有什麼代價？說明後等我決定。」

## 點數與界線

- 起草、推送、檢查和渲染都不消耗點數。
- 試玩會消耗點數，Agent 會先徵求你的同意。
- Agent 只會修改試玩卡和你自己的私人卡，不會替你送審或公開。
